**SECURITY**
argon2id password hashing. Enumeration-resistant responses (register/login/password-forgot return identical shapes regardless of account existence; login pays the same argon2 cost via a dummy hash comparison when no account matches). Redis-backed rate limiting, keyed by identifier so it applies even to nonexistent accounts. `AuthGuard` re-reads live user status and session revoked/expiry state from the database on every request — not just token validity — which is what makes logout, password reset, and reuse detection take effect immediately rather than waiting for the access token to expire.

**TESTS**
113 tests in `apps/api` (Phase 2's 91 was a repo-wide figure, not an apps/api-only count, so the two numbers aren't directly comparable — 113 is apps/api's own count as of this phase).

**VALIDATION**
typecheck, lint, format, full test suite, and production build all passed. Manually verified (no Docker in this sandbox): booted the compiled server against a deliberately unreachable Postgres AND Redis simultaneously — `/health` stayed 200, `/ready` correctly reported 503 with the real connection error, and `/auth/register` correctly reached the DB layer before failing with a clean 500 envelope. That manual test is what surfaced the `RateLimitGuard` bug below.

**DECISIONS**
`RateLimitGuard` fails **open** (allows the request, logs a warning), not closed, when Redis is unreachable — found via the manual outage test above: it originally let a Redis connection error propagate, turning a Redis outage into a total outage of the entire authentication surface, when rate limiting is meant as defense-in-depth, not the primary control. Separately, `OtpService`/`OtpChallengeRepository`'s `findActive()` query originally filtered `expiresAt: {gt: now}`, silently excluding expired challenges from ever being found and making the service's own `EXPIRED` check dead code (every expired code returned the same generic `INVALID` as a wrong code); fixed by renaming to `findLatestUnconsumed(ByHash)` with no expiry filter, so the service can distinguish "never existed" from "existed but expired." Also fixed: `apps/api`'s own `fastify` dependency resolved to a version incompatible with `@nestjs/platform-fastify`'s pinned version, breaking every `@fastify/*` plugin's type augmentation — pinned via `pnpm-workspace.yaml`'s `overrides`.

**KNOWN ISSUES**
No Docker — live Postgres/Redis integration (grants.sql, rate-limit persistence across restarts) remains unverifiable, as in every prior phase. No "set your phone" endpoint yet (that's profile management, Phase 5+), so `PHONE_VERIFICATION` is exercised at the service/OTP layer but has no realistic controller-level flow yet. Admin MFA (Phase 13) and staff-invitation acceptance (Phase 5) deliberately not implemented in this phase.

## PHASE 4 — Authorization

**IMPLEMENTED**
The permission catalogue (44 permissions × 7 roles) as typed data, `AuthorizationGuard` enforcing the three-part authorization check (authentication, role capability, resource scope), tenant resolution from `X-Restaurant-Id` or an implicit single membership, and 404-not-403 for cross-tenant resource access (logged as a `TENANT_ISOLATION_VIOLATION` audit event). `GET /auth/me` extended with `restaurantMemberships`.

**FILES**

**DATABASE**
None new.

**APIS**
`GET /auth/me` response shape extended (`restaurantMemberships`). No new business endpoints yet — Phase 4 is infrastructure that Phase 5 onward attaches to real routes.

**SECURITY**
Three-part check per docs/05-authorization-matrix.md §9.1: authentication, role capability, resource scope. `AuthorizationGuard` is deliberately **not** a global guard — Nest runs global guards before controller-level ones, and `AuthGuard` (Phase 3) is controller-level, so a global `AuthorizationGuard` would always run first and never see `request.user`; caught before any code exercised it, fixed by applying both explicitly per controller: `@UseGuards(AuthGuard, AuthorizationGuard)`. Cross-tenant resource access returns 404, not 403, so a tenant-scoped lookup failure never leaks whether the resource exists under a different tenant.

**TESTS**
73 new tests: 47 permission-catalogue tests (parsing the documented matrix as literal markdown-table text rather than a second hand-derived array, so a transcription slip can't pass by agreeing with itself — this caught that a first-draft test assertion, not the catalogue, was wrong about SUPER_ADMIN's order-management permissions), 15 guard unit tests, 11 end-to-end tests via a test-only probe controller (proving the full pipeline — 401/403/404 semantics, `X-Restaurant-Id` resolution, role-capability enforcement, mid-session staff disablement — ahead of any real endpoint using it). 186 tests total in `apps/api` (up from 113).

**VALIDATION**
typecheck, lint, format, full test suite, and production build all passed. Manually verified against simultaneously-unreachable Postgres and Redis, consistent with Phase 3's verified degradation behavior.

**DECISIONS**
`AuthorizationGuard` registered per-controller, never globally, so it's always guaranteed to run after `AuthGuard`.

**KNOWN ISSUES**
No real business endpoint uses these guards yet (Phase 5 attaches them to real routes). Admin roles (SUPPORT/ADMIN_OPERATIONS/ADMIN_FINANCE/SUPER_ADMIN) are encoded in the catalogue but unreachable — no `admin_users` table or login path exists until Phase 13.

**DECISIONS**

- BR-3's formula computed by summing packaging/delivery/platform fee/tax then subtracting a combined, capped discount (BR-6, BR-7) — promotion clamped against the discountable base first, loyalty against whatever remains, a deterministic priority order.
- Platform fee is basis points of the subtotal (`PLATFORM_FEE_BPS`, global config, default 0), not per-restaurant — matches a config var already scaffolded in `.env.example` ahead of this phase, tagged `[Phase 8+]`.
- Tax (`taxPercent`) is fully built and tested in the engine but never wired to a live value — BR-15 flags it as needing real tax advice, so the endpoint always passes none rather than guessing a rate.

**DECISIONS**

- **`MockDeliveryProvider.name = 'mock_delivery'`, not `'mock'`.** Caught during test-writing, before it shipped: `MockPaymentProvider` already claims the string `'mock'`, and `(provider, providerEventId)` is the entire `WebhookEvent` dedup/idempotency key — two unrelated integrations sharing one `provider` identity would have quietly defeated the point of that key being provider-specific, even though a random-UUID event-id collision between them was astronomically unlikely in practice. Matches the `Delivery` model's own doc comment, written during planning, which had already specified `mock_delivery` — the implementation had drifted from its own design note.
- **Dispatch triggered directly and synchronously from `RestaurantOrderService.ready()`**, not a new outbox-consumer type — mirrors Phase 10's reject-triggers-refund exactly, and a delivery dispatch is no more "fire and forget" than a refund is; both need a definite, observable outcome the same request cycle can reason about (even though the network call itself happens after the order-state transaction commits).
- **Delivery webhooks reuse `WebhookEvent`** rather than a second, parallel table — one webhook-processing pattern (verify → dedup-insert → apply → always-200) for every provider callback in the system, not two independently-maintained copies of it. Documented up front in the `Delivery` model's own schema comment before any code was written.
- **Order-state coupling always routes through `OUT_FOR_DELIVERY` first**, even when the real target is further along (`DELIVERED`, `DELIVERY_FAILED`) — `OrderStateService.transition()` only allows one hop and is itself idempotent-replay-safe, so walking both hops in sequence inside one webhook call is what lets an out-of-order `DELIVERED` (arriving while the order is still `READY_FOR_PICKUP`) apply cleanly without a special-cased "skip a hop" branch in the state machine itself.
- **No admin redispatch endpoint** — `delivery:redispatch` is scaffolded in the permission catalogue (Phase 4) but the actual endpoint is explicitly Phase 13 (Admin panel) per docs/04 §8.6. A `CREATION_FAILED`/stuck-`PENDING_CREATION` delivery today is visible (restaurant dashboard + the `DELIVERY_CREATION_FAILED` outbox alert) but not yet re-triggerable through the API — `DeliveryDispatchService.dispatch()` deliberately never re-attempts an existing row on its own.
- **`UBER_DIRECT_CUSTOMER_ID` added to the env schema mid-phase** — the real Uber Direct API scopes every call under a per-organization customer id in the URL path (`/customers/{customer_id}/deliveries`), which the original Phase 11 scaffolding (done ahead of this phase, before the adapter's actual request shape was known) hadn't anticipated. Added in the same commit as the code that reads it, per the env schema's own standing rule.

**KNOWN ISSUES**

- `UberDirectProvider` is a correct implementation of Uber Direct's published API (OAuth2 client-credentials, REST create/fetch/cancel, HMAC webhook verification) but is **genuinely unverified against the live API** — no credentials, no network access to Uber's servers in this sandbox. `DELIVERY_PROVIDER` defaults to `mock` for exactly this reason (RISK-3), and nothing in this codebase claims otherwise.

**DECISIONS**

- **Seed-only admin bootstrap, no HTTP endpoint to create an `AdminUser`.** The spec (docs/04-api-specification.md) defines no such route, and building one would mean either an unauthenticated admin-creation endpoint (unacceptable) or a "bootstrap first admin" flow the spec never asked for — so the gap is deliberate and spec-faithful, not an oversight. `prisma/seed.ts`'s `seedSuperAdmin()` is explicitly dev/pilot-only (own console warning at seed time).

Per-session verification, checked against the live row every request, closes it at the cost of re-verifying MFA on every new session (an accepted, standard tradeoff for admin-tier access).

Fixed by importing `PaymentsModule` directly (it already exports everything needed); confirmed by the full suite passing again. Documented in `admin.module.ts`'s own comment as a lesson caught during testing, matching this project's standing "corrections noted, not silently fixed" convention.
- **"DELIVERED cannot move to PREPARING" tested via its practical equivalent, not literally.** No endpoint exists for arbitrary order-status transitions (only accept/reject/preparing/ready/cancel), so the named acceptance criterion was proven as "a DELIVERED order rejects admin cancel with 409" — the same underlying graph property (no outbound edge from a terminal state) via the one path that actually exists.
- **`admin_users`'s `AdminRole`/`AdminUserStatus` reuse the exact enum values the Phase 4 permission catalogue already used**, rather than inventing new ones — zero drift between "the roles the authorization matrix understands" and "the roles a real row can hold."
- **`argon2` added to the root `package.json`'s `devDependencies`**, matching the version already pinned in `apps/api/package.json`. `prisma/seed.ts` is linted/type-checked under the root tsconfig, which had no type information for `argon2` (only pnpm's runtime hoisting made it resolvable at all) — the same rule already established by `@prisma/client` also being declared at the root for `seed.ts`'s sake.

**DECISIONS**

- **A real `SELECT ... FOR UPDATE` via `$queryRaw`, not this codebase's usual documented shortcut.** Every earlier lock-count-insert sequence in this project (`RefundService`'s INV-6 check, `OrderStateService`'s transitions) uses a plain `findUnique` with a comment explaining real Postgres would use `FOR UPDATE` here, left as an honestly-documented, never-fully-verified gap. This phase's headline acceptance criterion is explicit enough — both in `docs/02-database-schema.md` §6.3 ("do not substitute an unlocked count") and in `docs/13-implementation-phases.md`'s Phase 14 line ("especially N+1 concurrent claims on a limit-N coupon yield exactly N") — that a real lock was implemented and independently verified against real Postgres this phase (see VALIDATION), a deliberate strengthening beyond the established precedent, not a stylistic choice.
- **A real, previously-latent gap in the in-memory test fake, found and fixed while building the concurrency test:** `$transaction`'s interactive-callback form had never serialized concurrent invocations — under `Promise.all`, ten "concurrent" transaction callbacks would interleave in the microtask queue with no isolation at all, exactly the race a real database transaction prevents. This had never been caught before because no earlier phase's "concurrent claims" test actually depended on read-then-write atomicity spanning multiple awaited operations inside a transaction (Phase 9's "two concurrent identical checkouts" and Phase 11's "two concurrent dispatch() calls" both rely on a UNIQUE constraint rejecting the second insert, which needs no serialization to be correct). Fixed by chaining every interactive `$transaction` callback onto a shared promise queue, so the fake now provides the SAME observable guarantee real Postgres row-locking gives for a row two transactions actually contend on — coarser (global, not per-row) but strictly safe, and verified not to break any of the 422 pre-existing tests.
- **Per-customer and first-order-only limits keyed by `customerPhone`, not `customerId`.** The documented schema (docs/01-domain-model.md §5.8) lists `customer_id` as the redemption's per-customer key, but `CheckoutService` creates a brand-new `Customer` row on every single checkout (guest checkout has no durable identity, AMB-2) — `customerId` can never recognise the same real person across two orders. `customerPhone` (E.164-normalised, BR-26) is the only signal that does, so it is denormalised onto `PromotionRedemption` (the same call `Order.customerPhone` already makes) and is what the actual limit-enforcement queries use; `customerId` is retained on the row for referential/audit consistency with the documented schema, not dropped.
- **Discount amount reused from the pre-transaction quote, not recomputed a second time under the lock.** `PromotionReservationService.checkAndLock` returns only a pass/fail verdict plus the resolved `promotionId` — the `discountMinor` written to the `PromotionRedemption` row is the value `CheckoutQuoteService` already computed as literally the first step of `checkout()`. Recomputing pricing a second time under the lock, solely to defend against a promotion's terms changing in the sub-second gap between that call and this one, was considered and rejected as disproportionate to a race this narrow and not required by any named acceptance criterion — an explicit, documented scope boundary.
- **Code-based promotions only in this phase** — `Promotion.code` is required (not nullable), even though `docs/01-domain-model.md` §5.8 documents `code: null` meaning "automatic" (applied without entry). "Customer coupon entry" is the phase's own named frontend requirement (docs/13-implementation-phases.md); resolving which of several eligible automatic promotions would apply to an order with no code at all is a real, separate design problem with no acceptance criterion demanding it here.
- **`FREE_DELIVERY` is resolved to a `FIXED_AMOUNT` pricing-engine input capped at the order's real delivery fee**, computed in `PromotionEligibilityService.toPricingDiscountInput`, not a new branch inside `calculatePricing()` itself — keeps the Phase 8 pricing engine completely unchanged (still only PERCENTAGE/FIXED_AMOUNT internally) while still making FREE_DELIVERY structurally incapable of discounting more than the fee actually charged, regardless of what `Promotion.value` is set to.

- **`rating.recompute` runs synchronously, not as the debounced queue job docs/07-events-and-jobs.md names** — the same "in-process call instead of a new BullMQ job" call every phase has made since Phase 12's own notification retry scheduler. A full recompute is a single cheap aggregate query scoped to one restaurant; running it synchronously after every mutation makes `ratingAvg`/`ratingCount` provably never stale, which is a STRONGER guarantee than a debounced job would give, not a weaker one — BR-123's "reconcilable against source rows" is satisfied by construction rather than by a periodic catch-up.
- **Bayesian constants (`m=3.5`, `C=5`) are code-level defaults, not a product decision requiring sign-off** — unlike `PLATFORM_FEE_BPS` (explicitly named `[PD]` in docs/06), no business rule or ambiguity doc names specific values for these. Documented in the service's own doc comment with the reasoning (prevent small-sample-size gaming), changeable without a schema migration if a real product decision later supersedes it.
- **A restaurant with zero PUBLISHED reviews shows `ratingAvg: null`, never `0`** — the Bayesian formula would otherwise happily compute a fake "3.5-star, zero reviews" rating from the prior alone. `RatingAggregateService` special-cases `count === 0` explicitly rather than letting the formula's arithmetic produce a misleading number.
- **A real, previously-latent gap in the in-memory test fake, found via this phase's own new query pattern:** the `customer` table had `create`/`findUnique` but no `findMany` at all — nothing before this phase ever needed to look up more than one customer at once. **DECISIONS**

- **A real bug found ONLY by live verification: `LoyaltyAccountRepository.lockByCustomerId`'s `$queryRaw` failed against real Postgres with `operator does not exist: uuid = text` (error 42883) on every single call.** `customer_id` is a UUID column; Prisma's tagged-template `$queryRaw` interpolates every parameter as text regardless of the target column's real type, and Postgres has no implicit `uuid = text` comparison operator. Phase 14's own row-lock query (`PromotionReservationService.checkAndLock`, comparing `code`, a TEXT column) never hit this class of bug, and the in-memory test fake's `$queryRaw` stub is a plain string-match, not a real SQL type-checker — so all 460 automated tests, including the concurrent-redemption test, passed while every real HTTP redemption request 500'd. Fixed with an explicit `${customerId}::uuid` cast; re-verified live afterward with a clean result. This is the clearest demonstration yet in this project of why live-database verification is a required phase step and not a formality — the fourth genuinely new class of gap a live pass has caught (after Phase 12's stale-process port confusion, Phase 14's `$transaction` serialization gap, and Phase 15's customer.findMany gap), and the first one that would have shipped a 500 error on the phase's own headline acceptance criterion if live verification had been skipped.
- **`LoyaltyRedemption` (RESERVED/CONFIRMED/RELEASED) is a real entity this phase adds, even though docs/01 §5.9 lists only `LoyaltyAccount`/`LoyaltyLedger`.** BR-102 ("reserved at checkout and confirmed on payment capture, mirroring coupons") cannot be satisfied by the ledger alone without inventing a seventh, non-append-only-friendly ledger type for "reservation" and an eighth for "release" — both of which would violate BR-97's "never updated or deleted" more than a dedicated reservation row does. Mirroring `PromotionRedemption`'s exact three-state shape keeps every `LoyaltyLedger` row a genuine, permanent fact: a released reservation simply never produces one.
- **The redemption lock additionally subtracts other RESERVED-but-unconfirmed redemptions for the same customer — not just the cached balance — inside the same lock.** Unlike promotions (where the lock target, `usage_count`, IS the thing being contended over), a loyalty redemption's actual ledger debit is deferred to CONFIRM time, so `balancePoints` alone would still read "full" for a second concurrent request racing against a first request's not-yet-confirmed reservation. This is the one place this phase's design diverges from a literal copy of Phase 14's pattern, and it's the reason the concurrency test needed 5 requests against a real (small, deterministic) balance rather than relying on the row lock alone.
- **Redemption conversion rate (100 minor units / ₹1 per point) is a documented code-level default with no spec source** — AMB-11 names the EARN rate (`LOYALTY_POINTS_PER_100_INR`, an env-configurable `[PD]`-adjacent value already scaffolded in `.env.example`), but no doc names a REDEMPTION rate. Combined with the earn default, this is a 1% reward rate — a realistic, easily-explained pilot default, the same "no spec source, code-level default" treatment Phase 15 gave its Bayesian rating constants. `REFERRAL_REWARD_POINTS = 50` is the same category of decision, equally undocumented in the source material.
- **AMB-2's "no" on retroactive merge is followed literally: registering an account never links or backfills any prior guest `Customer` row sharing the same phone.** `CustomerRepository.createAccount` always creates a brand-new row; a phone's guest-checkout order history before registration is simply not visible to the new account. This was already the explicit recommendation ("the deduplication and fraud surface is not worth it"), not a shortcut taken under this phase's own time pressure.
- **`redeemLoyaltyPoints` was deliberately NOT added to `POST /public/checkout/quote`'s request DTO**, even though `loyaltyDiscountMinor` support was added to the underlying `CheckoutQuoteService.runQuote`/`quoteByRestaurantId` methods (used internally by `CheckoutService`). The quote endpoint is, and remains, fully unauthenticated (guests price-check too) — resolving a redemption needs a customer identity that endpoint structurally never has. This mirrors Phase 14's own coupon-preview boundary (a coupon's core terms don't depend on identity, so it gets a preview; loyalty inherently does, so it doesn't) rather than contradicting it.
- **The actual points reserved at checkout are derived from the pricing engine's CLAMPED discount, never the raw client request** — `minorToPoints(quote.breakdown.loyaltyDiscountMinor)`, not `input.redeemLoyaltyPoints` directly. If a customer requests more points than an order can actually absorb (e.g. after a promotion already consumed most of the discountable base), only the points corresponding to the discount actually applied are ever locked/spent — the same "never charge for value not received" principle the pricing engine already enforces for the promotion+loyalty stacking order (promotion first, loyalty against what remains, per AMB-10).
- **Admin adjustments never touch `lifetimeEarned`/`lifetimeRedeemed`, only `balancePoints`.** Those two fields are historical counters ("points ever earned/redeemed through the normal flow"); an admin correction is a different kind of event, and inflating "lifetime earned" via a goodwill credit would misrepresent a customer's real order-driven earning history.

**DECISIONS**

- **The two mid-phase fixes (attachment download, WAITING_CUSTOMER/RESTAURANT transitions) were found by re-reading each service's own contract against what its callers/tests could actually exercise, not by a user report.** `presignDownload` existed with a clear doc comment but zero callers — a dead method is a stronger signal than a missing one, since it means the author intended a consumer that was never wired up. `postReply`'s `matchingWaitStatus` check made no sense as dead code either: checking for a status nothing could ever produce is the kind of asymmetry worth chasing down rather than assuming intentional. Both are the same category of gap as every prior phase's "field already anticipated" pattern, just the write-side instead of the read-side.
- **`eslint`'s `no-unnecessary-type-assertion` and `tsc` briefly appeared to disagree on `Date.UTC(y!, m!, d!)`-style calls; they didn't.** `Date.UTC`'s third parameter (`date`) is optional and already accepts `undefined`, so `d!` was genuinely redundant even under `noUncheckedIndexedAccess`, while `y!`/`m!` (the required `year`/`monthIndex` positions) were not — removing all three at once (matching what looked like a uniform pattern across three destructured array elements) broke the build; removing only the truly-optional one fixed both tools at once. A reminder that "these three came from the same destructure" doesn't mean they have the same type-safety needs at each call site.
- **`WAITING_PROVIDER` remains unreachable by design, not by oversight this time.** Unlike the customer/restaurant WAITING_* states (which have a natural trigger — an agent's PUBLIC reply), no code path in this system ever needs a case to wait on an external delivery/payment provider's own support channel; adding a manual "mark as waiting on provider" admin action for a state nothing currently produces would be speculative scope, not a fix for a found gap.
- **Analytics rollups deliberately never read `AnalyticsEvent`** (see IMPLEMENTED) — the "reconciles with source data" acceptance criterion is trivially and permanently true as a result, rather than depending on the event-ingest pipeline (an "at least once," never "exactly once" outbox relay) never dropping or duplicating an event that a rollup would otherwise depend on.
- **`GET /admin/overview`'s response shape change (`ordersToday` → `metrics`) was made without a deprecation/compatibility shim.** No real external consumer of this endpoint exists yet (the only caller is this repo's own `apps/web` admin page, updated in the same commit) — adding a compatibility field for a consumer that doesn't exist would be exactly the kind of unnecessary abstraction this codebase avoids elsewhere.

- **Postgres Row-Level Security (docs/09 §15.3's explicitly "optional fourth layer") was evaluated and deliberately deferred, not implemented.** The three required layers (route guards, repository scoping, integration tests with explicit cross-tenant 404 assertions on every tenant-scoped endpoint across all 17 phases built so far) are real, tested, and have never been the source of a cross-tenant leak in this project's audit history. RLS would require wrapping every Prisma call in the entire codebase in a request-scoped transaction running `SET LOCAL app.current_restaurant_id` first — a genuine cross-cutting architecture change, not a contained addition, and speculative given the existing three layers already satisfy the threat model's own stated bar. Deferred, not rejected — revisit if a real incident or a specific compliance requirement materializes.
- **The concurrent-refund fix uses the same insert-and-let-the-constraint-decide pattern as every other idempotent write in this codebase, applied at a catch site instead of purely a pre-check.** A pre-check-only approach (what shipped before this phase) can never fully close a genuine race by itself — the database's own unique constraint is the only thing that can, and every other idempotent path in this codebase already relies on it as the actual guarantee, with the pre-check existing purely as a fast-path optimization to skip the transaction entirely on the (very common) exact-replay case.
- **New rate limits were chosen generously, not maximally restrictively** — see `SECURITY_AUDIT.md`'s Decisions section for the specific calibration reasoning (checkout: 20/hour; quote: 60/hour; password/reset and staff OTP verify: 10/15min, matching every other "verify a secret" endpoint already in this codebase).
- **The web app's CSP references a real external origin (Razorpay's checkout iframe, `https://checkout.razorpay.com`) even though real Razorpay integration remains unverified end-to-end in this environment** (no live credentials — a standing, previously-documented gap, unchanged by this phase). This is the correct production value regardless of local verification status, the same "wire the real shape now, verify against real credentials later" treatment `PAYMENT_PROVIDER`/`DELIVERY_PROVIDER` themselves already received starting Phase 9/11.

**KNOWN ISSUES**

- No penetration test against a deployed environment — there is no deployed environment yet (that's Phase 20). Every attack in this audit was tested via real HTTP requests against the real application code (in-memory-Prisma-backed in the automated suite, real Postgres/Redis in the live pass above), not a black-box test against running production infrastructure.
- The web app's CSP/HSTS/etc. headers were verified by reading `next.config.mjs`'s declarative `headers()` output and confirming the build compiles and serves correctly — not independently re-verified via a live `curl` against a running `next start` in this pass (the API's headers were; the web app's are pure Next.js config with no server-side logic that could diverge from what's declared, unlike the API's helmet registration which does have imperative registration order to get right).
