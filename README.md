# Direct-Order

Commission-free direct-ordering platform for independent Indian restaurants. Each restaurant gets a branded ordering link, a real-time order dashboard, online payments, and transparent visibility into every rupee — without giving up 25–35% of order value to an aggregator.

**Status:** Phase 15 (Reviews) — see [PRODUCT/docs/13-implementation-phases.md](PRODUCT/docs/13-implementation-phases.md). Foundation (Phase 1), core schema and tenancy (Phase 2), authentication (Phase 3), authorization (Phase 4), restaurant creation/onboarding/profile/staff/uploads (Phase 5), menu categories/items (Phase 6), the public ordering page (Phase 7), the pricing engine + server-side cart validation (Phase 8), order creation/checkout/payment verification/webhooks/refunds (Phase 9), the restaurant order queue with accept/reject/preparing/ready and a live SSE feed (Phase 10), delivery dispatch + provider webhooks (Phase 11), the notification pipeline + centre + preferences (Phase 12), the admin panel with role-based access and mandatory MFA (Phase 13), coupon promotions with race-safe usage limits (Phase 14), and customer reviews with Bayesian rating aggregates (Phase 15) are done. A customer can persist a cart, check out — optionally with a coupon code — pay (a mock provider by default — see Payments below), track their order by guest access token, and once it's delivered, leave a star rating and review; a restaurant can watch orders arrive live, accept or reject (with an automatic full refund) them, move them through preparation to ready-for-pickup, have a courier dispatched automatically the moment it's marked ready, receive an in-app/SMS/WhatsApp notification at every step, run its own coupon promotions, and respond publicly to reviews; a platform admin can log in, complete TOTP MFA, approve/suspend restaurants, cancel orders (with automatic refund), disable other admins, read a full audit trail, manage platform-wide promotions, and moderate reported reviews. **Phase 11 was the end of the pilot scope** (docs/13-implementation-phases.md: "At this point the product is commercially usable... deploy to staging and run a real pilot before continuing"); Phases 12–15 are built past that milestone, per the user's standing instruction to continue through all 20 phases without stopping for go-ahead. As of Phase 15 the full flow — registration through order fulfillment through delivery dispatch through notification through admin oversight through coupon redemption through review submission — has been run end-to-end against a real PostgreSQL/Redis stack via `docker compose up -d`, not just the in-memory test fakes, including a real Bayesian rating-aggregate recompute verified against a hand-checked formula; see Testing below.

Full specification: [PRODUCT/IMPLEMENTATION_HANDOFF.md](PRODUCT/IMPLEMENTATION_HANDOFF.md).

## Stack

TypeScript everywhere. Next.js 15 (frontend) · NestJS on Fastify (API) · PostgreSQL 16 + Prisma · Redis (rate limiting since Phase 3) · pnpm workspaces monorepo. Background work (outbox relay, order expiry, notification retry/backoff) runs as in-process pollers today, not BullMQ-backed queues — the original plan for real BullMQ consumers landing in Phase 12; see the Notifications section below for why that was deliberately deferred rather than silently dropped.

## Database roles

Two separate Postgres roles, deliberately (Phase 2, `docs/02-database-schema.md`):

- **`direct_order`** (`DATABASE_URL`) — the owner/migration role. Used only by `prisma migrate` and `pnpm db:grants`. Has full DDL privileges.
- **`direct_order_app`** (`APP_DATABASE_URL`) — the restricted runtime role the API and worker actually connect as. Created locally by `infrastructure/postgres/init/01-create-app-role.sql` on first `docker compose up`; its table-level privileges come from `prisma/grants.sql`, applied via `pnpm db:grants` after every migration.

The point: even if application code were compromised or buggy, it cannot rewrite `audit_logs` — `direct_order_app` is granted `SELECT, INSERT` on that table only, never `UPDATE`/`DELETE`, enforced by Postgres itself rather than trusted to application code alone.

Production provisions its own equivalent roles through the platform's secret manager, not these files.

## Authentication

Registration, login, logout, refresh, password reset, and email/phone verification (Phase 3, `docs/09-security.md` §15.2). A few load-bearing decisions worth knowing before touching this code:

- **Sessions, not just tokens.** Access tokens are short-lived JWTs (15 min) carrying `{sub, sid}`, but `AuthGuard` re-checks both the user's status and the referenced `Session` row's live/revoked status on every request — logout, password reset, and refresh-token-reuse detection all take effect immediately, not after the token happens to expire.
- **Refresh-token rotation with reuse detection.** Every `/auth/refresh` call issues a new refresh token and revokes the old one. Presenting an already-rotated token revokes the entire session family and logs a `SESSION_REUSE_DETECTED` audit event — see `SessionService.rotate()`.
- **Enumeration resistance.** `/auth/register`, `/auth/login`, and `/auth/password/forgot` return identical responses (and, for login, comparable timing via a dummy password-hash comparison) regardless of whether the account exists.
- **Rate limiting fails open.** `RateLimitGuard` allows a request through — logging a warning — if Redis is unreachable, rather than taking down the entire authentication surface over a rate-limiter dependency outage. It is defense-in-depth, not the primary control.
- Cookies (`do_access_token`, `do_refresh_token`) are `HttpOnly; SameSite=Lax; Path=/`, and `Secure` outside `APP_ENV=local` (a plain-HTTP `Secure` cookie would never reach the API in local development).
- **CSRF: double-submit cookie, on top of SameSite=Lax.** A non-HttpOnly `do_csrf_token` cookie is set on every request (`platform/security/csrf-cookie.hook.ts` — a native Fastify `onRequest` hook, deliberately not `NestMiddleware`: chaining two Nest middlewares through `@fastify/middie` produced a real, reproducible "reply.code is not a function" bug under concurrent requests during Phase 5 development). Every non-GET request must echo it back as `X-CSRF-Token`, checked by the globally-registered `CsrfGuard`; `apps/web`'s `api-client.ts` reads the cookie and attaches the header automatically.

## Authorization

Permission catalogue, role definitions, and the tenant-isolation guards (Phase 4, `docs/05-authorization-matrix.md`). Answers the three questions every request must pass: authentication (Phase 3's `AuthGuard`), role capability (`@Permissions(...)`), and resource scope (`@TenantScoped()`).

- **Two decorators, one guard.** A tenant-scoped, permission-gated route declares `@TenantScoped()` and `@Permissions('menu:write')`; `AuthorizationGuard` (`platform/authorization`) reads both. It is **not** a global guard — Nest runs global guards before controller-level ones, and it depends on `AuthGuard` having already populated `request.user`, so every tenant-scoped controller applies both explicitly and in order: `@UseGuards(AuthGuard, AuthorizationGuard)`.
- **403 vs 404, deliberately different layers.** Sending `X-Restaurant-Id` for a restaurant the caller has no active membership in is **403** (`AuthorizationGuard`, logged as a `TENANT_ISOLATION_VIOLATION` audit event). Successfully resolving a tenant and then requesting a specific _resource_ that belongs to a different restaurant is **404**, not 403 — returning 403 would confirm the resource exists, leaking tenant structure (`docs/04-api-specification.md` §8.1). Domain modules get this for free by passing a tenant-scoped repository lookup's `null` result through `assertTenantResourceFound()`.
- **Membership is re-checked per request**, exactly like Phase 3's session liveness check — a staff member disabled mid-session loses access on their very next request, not when their token happens to expire.
- **Restaurant roles (STAFF/MANAGER/OWNER) and platform admin roles (SUPPORT/ADMIN_OPERATIONS/ADMIN_FINANCE/SUPER_ADMIN) are both enforceable** as of Phase 13 — the permission catalogue's full admin matrix was built in Phase 4, anticipating this exactly; Phase 13 only added the `admin_users` table and `AuthorizationGuard`'s admin-resolution branch, not a new permission system. See Admin panel below.
- Proved ahead of any real endpoint via a test-only probe controller (`apps/api/test/authorization.e2e.test.ts`) before Phase 5 attached it to real routes — every `/restaurant/*` controller below uses exactly that pattern.

## Restaurants

Restaurant creation, onboarding, profile/branding/settings, staff invitations, and presigned image uploads (Phase 5, `docs/13-implementation-phases.md`). Every `/restaurant/*` route is `@UseGuards(AuthGuard, AuthorizationGuard)` plus `@TenantScoped()` + `@Permissions(...)` per handler — see Authorization above.

- **`POST /restaurants` creates the tenant** — ownership is always the authenticated principal, and `slug` is optional (auto-derived from `name` with silent `-2`/`-3` disambiguation) or explicit (validated against the reserved-word list and uniqueness, **rejected**, not silently renamed, if either fails — `RestaurantService.validateExplicitSlug`).
- **Onboarding is two independent state machines**, deliberately not one: `Restaurant.onboardingStatus` (the owner's own wizard progress: `IN_PROGRESS` from the moment of creation → `COMPLETED` on submit) and `Restaurant.status` (platform-controlled lifecycle: `DRAFT` → `PENDING_APPROVAL` on submit → `ACTIVE` only once an admin approves, Phase 13). Submitting requires a saved pickup address; both transitions happen server-side in `RestaurantProfileService.submitOnboarding`, so clearing browser storage cannot un-submit or fake completion.
- **Last-active-OWNER protection** (`StaffManagementService`) blocks demoting or disabling a restaurant's sole OWNER with `409 LAST_OWNER` — checked before the (separate) self-demotion guard, so the common case where both would apply surfaces the more specific code.
- **Presigned uploads, two steps.** `POST /restaurant/uploads/presign` validates the _declared_ content type/size (SVG rejected outright, 5 MB cap) and returns a time-limited PUT URL — the API never sees the bytes at this step. `POST /restaurant/uploads/verify` fetches what actually landed in storage afterward and checks the magic bytes match what was declared (`uploads/magic-bytes.ts`), deleting and rejecting on any mismatch — the only way to catch a `.exe` renamed to `.jpg`, since the declared type alone proves nothing.
- **Storage is S3-compatible** (`uploads/s3-storage.adapter.ts`, MinIO locally via `docker-compose.yml`) behind a `StoragePort` interface — tests substitute an in-memory fake (`test/support/fake-storage.ts`) rather than requiring live MinIO.
- **Permanent ordering link + QR code** (`/restaurant/profile`, "Ordering link & QR code") — `{origin}/r/{slug}`, generated entirely client-side (the `qrcode` package) and never persisted anywhere: since `slug` cannot be changed once set (no endpoint exists to change one — see the onboarding note above), encoding the same URL always produces the same QR code, so "the link and QR are never regenerated" falls out of that determinism rather than needing a stored image or a new DB column.

## Menu

Categories and items, CRUD + archiving + reordering (Phase 6, `docs/13-implementation-phases.md`). Same guard/permission pattern as Restaurants above (`menu:read`/`menu:write`/`menu:availability`).

- **Never hard-deleted.** "Delete" in the UI means archive (`archivedAt` set, `isActive`/`isAvailable` flipped off) — a row a later phase's order references for display context must still exist, per its schema.prisma doc comment.
- **Three states, not one:** `isActive` (on the menu) · `isAvailable` (orderable right now — the one field STAFF, not just MANAGER/OWNER, can toggle: `PATCH /restaurant/menu/items/:id/availability` is `menu:availability`, every other write is `menu:write`) · `archivedAt` (removed, retained for history). Don't conflate them.
- **Reordering is one transaction, validated before any write.** `POST /restaurant/menu/{categories,items}/reorder` first checks every id in the batch belongs to the caller's tenant; an unknown or foreign id fails the whole request with the previous order completely intact, rather than applying a prefix of the batch.
- **Category name uniqueness (among non-archived rows) is enforced at the service layer, not a DB constraint** — Prisma's schema DSL can't express a partial unique index, the same limitation already noted for `User`'s email-or-phone invariant.
- **Frontend reordering is dual-input:** native HTML5 drag-and-drop for mouse users, plus keyboard-focusable ▲/▼ buttons that do the same reorder call — an `aria-live` region announces the result for screen readers, since a drag's visual reshuffle is otherwise silent to them.

## Availability and the public ordering page

`isAcceptingOrders()` (Phase 7, `apps/api/src/modules/availability/availability.service.ts`) is **the single authority** on whether a restaurant can take an order right now — consumed by the public page today, and by search's "open now" filter and checkout revalidation once those phases exist, so all three always agree (docs/03-state-machines.md, BR-66).

- **Precedence, first match wins:** `Restaurant.status` → an active `ClosurePeriod` → `SpecialHours` (a date-specific override, if one exists for that date — replaces `OperatingHours` for that day entirely, doesn't merge with it) → `OperatingHours` (the weekly recurring schedule, overnight shifts spanning midnight supported) → `Restaurant.orderingEnabled`. A restaurant with `status: SUSPENDED` can never make itself orderable by flipping `orderingEnabled` — `status` is checked first, unconditionally.
- **Everything is evaluated in the restaurant's own IANA timezone**, via `Intl.DateTimeFormat`, never the server's — see `availability/timezone.ts`. `OperatingHours.opensAt`/`closesAt` are Postgres `TIME` columns (wall-clock time-of-day only), round-tripped through an epoch-date convention documented in `availability/time-of-day.ts`.
- **Restaurant-facing management:** `GET/PUT /restaurant/hours` (full weekly replace, MANAGER+), `GET/POST/DELETE /restaurant/closures` (temporary closures — `DELETE` ends one early by setting `endsAt`, never a hard delete), `PATCH /restaurant/availability` (the `ordering_enabled` toggle, STAFF-permitted). `SpecialHours` has no restaurant-facing write endpoint yet (not in docs/04-api-specification.md §8.5) — the table and the precedence logic are fully built and tested; a later phase can add the write path without touching the authority function.
- **`GET /public/restaurants/:slug` and `/menu`** (`apps/api/src/modules/public/`) are unauthenticated and slug-keyed — the highest-risk leak surface in the API, so the response is an explicit field allowlist, never a spread of the Prisma row (asserted directly in `public.e2e.test.ts`). DRAFT/PENDING_APPROVAL restaurants 404 exactly like a nonexistent slug; ACTIVE/SUSPENDED/CLOSED are all visible (200) with a non-accepting `availability` decision for the latter two, so a bookmarked link still explains itself instead of just disappearing.
- **The customer page** (`apps/web/src/app/r/[slug]/`) is a real Server Component with dynamic metadata/Open Graph tags — not a client-side spinner. The cart is client-side, persisted to `localStorage` under a **per-slug key**, which is what makes "switching restaurants never mixes their items" true by construction rather than a runtime check. In-page search filters the already-fetched menu client-side; there is no separate search endpoint (cross-restaurant discovery is feature-flagged off, BR-146).
- **Playwright coverage runs against a mock API**, not a live database (`apps/web/e2e/support/mock-public-api-server.mjs`, wired in via a second `webServer` entry in `playwright.config.ts`) — this sandbox has no Docker/Postgres to seed a real restaurant against. Actually running `pnpm test:e2e` end-to-end for (apparently) the first time in this environment surfaced a real, unrelated pre-existing gap: every page mounts `SessionProvider` (Phase 3), which checks `GET /auth/me` on load — Chrome itself logs any non-2xx resource load as a console error regardless of how gracefully the app handles the response, so `smoke.spec.ts`'s original "zero console errors" assertion was never actually compatible with a logged-out visit once that session check existed. Fixed by allowing exactly that one expected, benign 401 message rather than loosening the assertion generally.

## Pricing engine and cart validation

The pricing engine (`packages/money/src/pricing.ts`, `calculatePricing()`) is **the single place order totals are computed** — Phase 8 builds it and `POST /public/checkout/quote`; Phase 9's real checkout, and every later phase that touches a total (promotion redemption, loyalty redemption, refund calculation), calls this same function rather than re-deriving one.

- **BR-3:** `payableTotalMinor = itemsSubtotal + packagingFee + deliveryFee + platformFee + tax − discount`, discount being promotion + loyalty, combined and capped so it can never exceed the discountable base (BR-7) or push the total negative (BR-6). Promotion is clamped against the base first, loyalty against whatever remains — a deterministic priority order, not a simultaneous split.
- **BR-5:** every percentage (tax, a percentage-type promotion, the platform fee) is rounded half-up to the nearest paise **once**, at the point of calculation — reusing `percentageOf()` from Phase 1, never re-rounding a later sum.
- **Platform fee is basis points of the subtotal** (`PLATFORM_FEE_BPS`, global config, default 0 — BR-14: zero renders as an absent line, not a "₹0 platform fee" one), not per-restaurant; no `RestaurantSettings` field exists for this.
- **`POST /public/checkout/quote`** runs the pricing-relevant subset of the mandated checkout sequence (docs/04-api-specification.md §8.3: availability, live item state, price-drift detection, minimum order, a coupon preview since Phase 14, then pricing) without the parts that need infrastructure this phase doesn't build — a persisted cart (`POST /public/carts`, Phase 9), loyalty reservation (Phase 16), or order creation (Phase 9). It takes cart contents directly in the request body rather than a `cartId`. Issues (`ITEM_UNAVAILABLE`, `PRICE_CHANGED`, `BELOW_MINIMUM_ORDER`, `RESTAURANT_UNAVAILABLE`, `COUPON_INVALID`/`COUPON_EXHAUSTED` since Phase 14) come back in a 200 response, not a single fatal error — `valid: false` is what actually blocks proceeding, and the breakdown is still computed from whatever items passed validation.
- **The frontend cart** (`apps/web/src/app/r/[slug]/restaurant-ordering-view.tsx`) re-quotes on every cart change and renders the server-computed breakdown plus any issue messages — there is no client-side price estimate anywhere; the number shown is always what the server just said.
- **Tax has no restaurant-level config yet** (BR-15 is explicitly flagged as needing real tax advice) — the engine supports a `taxPercent` input and is fully tested against it, but the live endpoint always passes none, the same "build it, don't wire it to a guess" treatment `SpecialHours` got in Phase 7.

## Orders, checkout, and payments

The mandated checkout sequence (`docs/04-api-specification.md` §8.3), the highest-risk endpoint in the project (Phase 9). `POST /public/carts` persists a browser cart server-side (guest-token-owned, 24h TTL); `POST /public/checkout` re-runs the exact same validation `POST /public/checkout/quote` already exercises (`CheckoutQuoteService.quoteByRestaurantId` — one function, not two), then creates `Order` (`PENDING_PAYMENT`) + `OrderItem` snapshots + `Payment` (`CREATED`) + status history in one transaction, and a provider payment intent afterward.

- **`PaymentProvider` port/adapter** (`apps/api/src/modules/payments/providers/`), the same shape as Phase 5's `StoragePort`: a `MockPaymentProvider` (the default — `PAYMENT_PROVIDER=mock`, no live network access needed) and a `RazorpayPaymentProvider` (correct against Razorpay's real, documented REST API and HMAC webhook scheme, but **unverified against the live API** — this sandbox has neither credentials nor network access to it, same honesty standard as Uber Direct in Phase 11). Payment settlement structure is a blocking open product/legal decision (AMB-3) — nothing here processes real money on an assumption.
- **Idempotency, not a guess.** `Order.(restaurantId, idempotencyKey)` is a real unique constraint — a client-generated `Idempotency-Key` header is required on `POST /public/checkout`, a pre-check replays a sequential retry (double-click), and a `P2002`-catch-and-refetch handles a genuine concurrent race, so exactly one order is ever created either way. A replay can't reissue the original raw guest access token (only its hash is ever persisted, same pattern as staff invitations) — a documented, deliberate scope boundary, not an oversight.
- **`OrderStateService`** (`apps/api/src/modules/orders/services/order-state.service.ts`) encodes the **full** order state graph (docs/03-state-machines.md §7.1) — every transition validates legality, locks the row, writes state + history in one transaction, and answers 409 (illegal) or 200-idempotent (already there) per the universal rules. Phase 9 drove only `PENDING_PAYMENT → PLACED/PAYMENT_FAILED/EXPIRED`; Phase 10's restaurant order management (below) is the first caller of the `PLACED → ACCEPTED/REJECTED` and `ACCEPTED/PREPARING → PREPARING/READY_FOR_PICKUP` edges through a real endpoint, reusing this exact same service unchanged.
- **Payment state is authoritative only from the provider, never the client** (BR-37). `POST /public/orders/:orderNumber/verify-payment` fetches fresh status from the provider and applies it through `PaymentVerificationService.applyProviderStatus` — the exact same method the signature-verified webhook receiver (`POST /webhooks/razorpay`) calls after independently re-fetching from the provider, so a webhook and a frontend poll can never disagree. An amount/currency mismatch never marks a payment captured — it's withheld and raises a `CRITICAL` `ReconciliationIssue` instead.
- **Webhook processing follows the documented contract exactly:** verify the HMAC signature over the _raw_ body (constant-time compare) → `INSERT ... ON CONFLICT DO NOTHING` on `(provider, providerEventId)` → zero rows means duplicate, stop, 200 → otherwise process → always 200 for a validly-signed, stored event, even if processing itself later fails (the event is marked `FAILED` and can be retried, but the provider is never told to retry a webhook already durably recorded). An invalid signature is rejected before any DB write at all, so a forged payload can't poison the dedup anchor.
- **Refunds** (`RefundService`) lock the payment row, sum non-`FAILED` refunds, and reject anything that would push the total above `capturedMinor` (INV-6) — inside the same transaction as the insert. Its first real HTTP caller is Phase 10's order rejection (below); admin-initiated manual/goodwill refunds still need a future Admin module.
- **Unpaid orders expire automatically** — a lightweight in-process `setInterval` scanner (`OrderExpiryScheduler`, `ORDER_PAYMENT_TTL_MINUTES`, default 30) moves stale `PENDING_PAYMENT` orders to `EXPIRED` through the same `OrderStateService`, so an order that got paid a moment earlier is never double-moved. Side effects (notifications, the outbox relay) are the same honestly-scoped placeholder as `OutboxService`'s log-only relay — real consumers attach in Phase 12, per `apps/worker`'s own standing doc comment.

## Restaurant order management

The restaurant-facing order queue and lifecycle actions (`docs/04-api-specification.md` §8.5, Phase 10) — `GET /restaurant/orders` (cursor-paginated, filterable by status), `GET /restaurant/orders/:id`, and `POST /restaurant/orders/:id/{accept,reject,preparing,ready}`, all `STAFF`-permitted, all tenant-scoped like every other `/restaurant/*` route.

- **No new state-transition logic** — every action calls the same `OrderStateService.transition()` Phase 9 built for the full graph. `RestaurantOrderService`'s only real job is the tenant-ownership pre-check (404, not 403, for a resource in a different restaurant — the same pattern every other domain module uses) and triggering a refund on rejection.
- **Reject → automatic full refund, structurally exactly-once.** `OrderStateService.transition()`'s own locked idempotent replay guarantees only the caller that actually applies `PLACED → REJECTED` ever sees `applied: true` (docs/03-state-machines.md §7.1: "Exactly one refund can ever be triggered") — `RestaurantOrderService.reject()` gates the `RefundService.requestRefund()` call on exactly that flag, so two staff rejecting simultaneously, or the same staff member double-clicking, can never produce two refunds. The refund's own idempotency key is derived from the order id, not client-supplied.
- **`GET /restaurant/orders/stream`** is Server-Sent Events (`@Sse()`), chosen per docs/04 §8.5 over WebSockets for one-directional server→client traffic and automatic browser reconnection. It is explicitly **a latency optimisation, never the source of truth** — a lightweight DB-poll `Observable` (`OrderStreamService`, 3s interval) replays `OutboxEvent` rows for the caller's own restaurant since a `Last-Event-ID`/`?lastEventId=` cursor (`OutboxEvent.restaurantId`, added this phase, backs the per-tenant replay query); the frontend also polls the real queue every 15s regardless, so a dropped or entirely-unavailable stream can never cost a restaurant a paid order. Skipped client-side for a staff member belonging to more than one restaurant — `EventSource` cannot set the `X-Restaurant-Id` header `AuthorizationGuard` needs to disambiguate, and that guard was deliberately not touched to work around it; those accounts rely on the 15s poll alone.
- **The dashboard** (`apps/web/src/app/restaurant/orders/`) shows the actionable queue (`PLACED`/`ACCEPTED`/`PREPARING`/`READY_FOR_PICKUP` — not a full historical ledger), plays a short generated tone and announces via an `aria-live` region on a genuinely new `PLACED` order (deduplicated against orders already seen this session, never re-alerting on a later poll), and never applies an SSE event's payload directly to local state — every event just triggers a real refetch of the order list.
- **Verified against a real, live PostgreSQL/Redis stack this phase** (`docker compose up -d && pnpm db:migrate && pnpm db:grants`) — the entire schema accumulated since Phase 2 applied cleanly on the first attempt, and the full flow (register → verify → login → create restaurant → menu → hours → public browse → cart → checkout → mock payment capture → verify-payment → order queue → accept → preparing → ready, plus a live SSE connection showing real events with correctly-populated `fromStatus`) was run end-to-end against it via curl. This surfaced one real bug — `MockPaymentProvider.fetchPaymentStatus` threw a bare `Error` for an unrecognized `providerPaymentId`, producing an opaque 500 instead of a typed 4xx/5xx the client could handle — fixed to throw the same `ProviderError` `RazorpayPaymentProvider` already uses for every provider-side failure. Real-database row-locking (`SELECT ... FOR UPDATE`) under genuine concurrent load is still unverified — a single manual walkthrough exercises the happy path, not a concurrency stress test — see PHASE_REPORTS.md for the full account.

## Delivery

Delivery dispatch and provider webhooks (`docs/03-state-machines.md` §7.4, `docs/04-api-specification.md` §8.6, Phase 11) — no new customer- or restaurant-facing HTTP endpoints beyond the webhook receiver; delivery status is embedded directly into the existing guest tracking (`GET /public/orders/:orderNumber`) and restaurant detail (`GET /restaurant/orders/:id`) responses, per the spec.

- **`DeliveryProvider` port/adapter** (`apps/api/src/modules/delivery/providers/`), the same shape as `PaymentProvider`: a `MockDeliveryProvider` (the default — `DELIVERY_PROVIDER=mock`, simulates the full lifecycle including failures, no live network) and a `UberDirectProvider` (correct against Uber Direct's real, documented OAuth2 + REST API, but **unverified against the live API** — RISK-3, docs/15-ambiguities-and-risks.md: "Uber Direct self-serve access in Bengaluru unconfirmed... never claim production delivery when mocked"). `MockDeliveryProvider.name` is deliberately `mock_delivery`, not `mock` — sharing `MockPaymentProvider`'s identity string would have quietly defeated the webhook dedup key below (caught before it shipped).
- **Dispatch is triggered directly from `RestaurantOrderService.ready()`**, gated on `result.applied` — the same structurally-exactly-once pattern Phase 10's reject-triggers-refund already established, not a new outbox-consumer abstraction. The real defence against a duplicate dispatch is `Delivery.@@unique([orderId])`: `DeliveryDispatchService` always attempts an insert and lets the constraint decide, so "mark ready" twice — sequentially or concurrently — creates exactly one delivery row, verified both via HTTP replay and via two genuinely concurrent `dispatch()` calls in tests.
- **Timeout ≠ failure.** A provider call that times out (`ProviderError` 503) leaves the delivery at `PENDING_CREATION` with the attempt recorded, never `CREATION_FAILED` — a future retry reconciles rather than blindly re-attempting on an ambiguous outcome. A definite rejection (502) does mark `CREATION_FAILED` and raises a `DELIVERY_CREATION_FAILED` outbox alert (restaurant + admin, same log-only-relay honesty as every other outbox event today) — the order itself stays at `READY_FOR_PICKUP`, never a false `OUT_FOR_DELIVERY`, because dispatch failure and the order transition are structurally independent.
- **Delivery webhooks reuse `WebhookEvent`** — no second, parallel `delivery_events` table. `(provider, providerEventId)` is already provider-specific and globally unique per provider, exactly what a delivery callback's `provider_event_id` needs. `POST /webhooks/delivery/:provider` (raw-body HMAC, `@SkipCsrf()`) 404s if `:provider` doesn't match the currently-configured `DELIVERY_PROVIDER`.
- **Order coupling is one-directional and rank-based**, never a raw status copy: courier-assigned-or-later events drive `READY_FOR_PICKUP → OUT_FOR_DELIVERY` (and `→ DELIVERED`) through `OrderStateService.transition()`, walking both hops in one webhook call when needed so a `DELIVERED` event arriving before `PICKED_UP` is applied directly rather than erroring — the out-of-order case named in the acceptance criteria. A regression (a stale event reporting an earlier stage after a terminal status) is logged and ignored, never applied backwards. `Delivery` state never touches `Payment`/`Refund` records.
- **Verified against a real, live PostgreSQL stack this phase** — `pnpm db:migrate` applied the `deliveries` table cleanly, `pnpm db:grants` confirmed the restricted runtime role can read/write it, and a full curl-driven walkthrough (register → restaurant → menu → checkout → payment → accept → preparing → ready) confirmed a real `Delivery` row is created with `provider = 'mock_delivery'`, then a correctly-signed mock webhook was POSTed and confirmed `PROCESSED` directly in the real `webhook_events` table, and the guest tracking endpoint returned the customer-safe delivery subset (status/courier/tracking only — no provider identity, ids, or fees). See PHASE_REPORTS.md for the full account.

## Notifications

The full pipeline docs/08-search-and-notifications.md §14.1 draws — `domain event → resolve recipients → apply preferences → create Notification per (recipient, channel) → adapter → provider` (Phase 12) — restricted to the event types the codebase's existing domains (orders, payments, delivery) actually produce; loyalty/referral/review/support/promotion catalogue rows have no producer yet, so they're not wired.

- **No new `NotificationEvent` table.** `OutboxEvent` already IS "the domain event record" this system produces — the same reuse call Phase 11 made for `WebhookEvent`. `Notification.@@unique([outboxEventId, recipientType, recipientId, channel])` is the structural dedup guarantee (docs/14.1): a duplicate event delivery always attempts an insert and lets the constraint decide, never a separate existence check first.
- **`NotificationChannelAdapter` port/adapter**, one per external channel (`apps/api/src/modules/notifications/channels/`) — `console` (default for SMS/WhatsApp/Email, logs instead of calling a real provider) plus real adapters for MSG91 (SMS), Gupshup (WhatsApp), and Resend (Email), each correct against its provider's documented API but **unverified against the live API**, the same honesty standard as every other real adapter in this codebase. `IN_APP` has no adapter — creating the row already is the delivery.
- **`OutboxService.registerConsumer()`** — a runtime hook, not a module import in either direction, added specifically so `NotificationDispatchService` (a domain module) can attach to the platform-layer outbox relay without `platform/outbox` ever importing a domain module (docs/12-repository-structure.md's dependency-direction rule: platform never depends on a domain module). `NotificationDispatchService` registers itself in its own `onModuleInit()`.
- **Retry/backoff/dead-lettering runs on the same lightweight in-process poller pattern** used everywhere else in this codebase (the outbox relay, `OrderExpiryScheduler`) — **not** the real BullMQ-backed `notifications` queue docs/07-events-and-jobs.md §12 and this file's own Stack section describe for this exact phase. A deliberate, documented scope decision (see PHASE_REPORTS.md's Phase 12 entry): every acceptance criterion is still genuinely satisfied (exponential backoff computed exactly per docs/07 §12's 1s→4s→16s→64s→256s schedule, dead-lettering after 5 attempts, a provider outage never rolling back business state), just without introducing a new queue infrastructure layer in the same phase that also builds the entire notification domain model.
- **A provider outage never rolls back an order, payment, or refund (BR-126)** — `NotificationDispatchService` runs strictly after the triggering transaction has already committed, in the outbox relay's own separate tick, and every failure is caught locally; nothing in the pipeline ever throws out to its caller.
- **Marketing requires explicit consent (BR-129)** — `Customer.marketingConsentAt`, checked before ANY `MARKETING`-category send regardless of channel preference; account creation is explicitly not consent. No `MARKETING` notification type is wired to a producer yet, so this guard is built and unit-tested complete with no real caller today — the same "no real caller yet" treatment `RefundService` got in Phase 9.
- **`/me/notifications*`, `/me/notification-preferences`** (Phase 12) serve the `RESTAURANT_USER` recipient type only — guest checkout is still the pilot default (AMB-2, unchanged since Phase 9), so there is no registered customer session to authenticate a customer-facing notification centre against yet. Customer-recipient `Notification` rows still get created and sent (SMS/email); they're just not readable through this HTTP surface. `PATCH .../notification-preferences` rejects (409) any attempt to disable `TRANSACTIONAL`/`SECURITY` before ever touching the database — the enforcement point is the service, not "does a preference row happen to exist."
- **Verified against a real, live PostgreSQL stack this phase** — real `notifications`/`notification_preferences` tables (migration applied cleanly, grants confirmed on the restricted role), then a full curl-driven walkthrough through checkout → accept → preparing → ready, waiting for the **real** 5-second outbox relay timer (not a test harness) to fire, confirmed real `Notification` rows landed in real Postgres for every order-lifecycle event, readable through the real `/me/notifications` and `/me/notifications/unread-count` endpoints. This run also exercised a genuine, previously-untested branch for real: the live-registered owner had no phone number on file, so `SMS`/`WHATSAPP` rows correctly came back `SUPPRESSED` ("No phone number on file") rather than erroring — exactly the intended behavior, confirmed against real infrastructure rather than assumed from the code.

## Admin panel

Role-based platform administration with mandatory per-session MFA (`docs/13-implementation-phases.md`, `docs/14-acceptance-criteria.md`, Phase 13) — `/admin/*` routes for restaurant approval/suspension, cross-tenant order/payment/user visibility, admin cancellation with refund, admin-account management, and a read-only audit log.

- **TOTP (RFC 6238) implemented from scratch** (`apps/api/src/modules/identity/services/totp.service.ts`), using only `node:crypto` — no new npm dependency, the same "bespoke auditable adapter over an unverifiable third-party dependency" call already made for the Razorpay/Uber Direct REST clients. Verified against all 5 official RFC 6238 Appendix B test vectors.
- **No new permission system.** `permission.catalogue.ts`'s full admin matrix (SUPPORT/ADMIN_OPERATIONS/ADMIN_FINANCE/SUPER_ADMIN, disjoint capability sets except SUPER_ADMIN's explicit superset) was already built in Phase 4, anticipating this phase exactly. Phase 13 only added the `admin_users` table and extended `AuthorizationGuard`'s existing `!isTenantScoped` branch to resolve an admin principal instead of building a second guard.
- **MFA is enforced per session, not per user.** `Session.mfaVerifiedAt` — a still-valid session from before MFA verification does not silently gain admin access; verification is proven once per session via `POST /auth/mfa/verify`, checked against the live session row (never the JWT), mirroring the existing "AuthGuard re-checks live DB state, never trusts the JWT alone" pattern already used for session revocation.
- **No HTTP path creates an AdminUser.** The spec defines no such endpoint, so none was built — the seed script (`prisma/seed.ts`) bootstraps the first SUPER_ADMIN directly, a deliberate, spec-faithful gap rather than an oversight.
- **Suspending a restaurant blocks new orders with zero new business logic.** `isAcceptingOrders()` (Phase 7's one-authoritative-function) already keys off `restaurant.status !== 'ACTIVE'`; admin suspend/reinstate only needed a correctly-validated state transition, not a second availability check.
- **Admin cancel reuses the exact refund path** order rejection already uses (`RefundService.requestRefund`, INV-6-guarded) — no parallel admin-only refund code.
- **A real stateful-provider DI bug, caught by the existing test suite, not written intentionally:** `AdminModule` originally re-provided `MockPaymentProvider` and friends as its own providers instead of importing `PaymentsModule`, creating a second, empty-state instance of a class that holds real in-memory Maps — broke 5 pre-existing tests. Fixed by importing `PaymentsModule` directly; now documented in `admin.module.ts`'s own comment as a lesson caught during testing, not a style choice.
- **Verified against a real, live PostgreSQL stack this phase** — `pnpm db:migrate` applied the `admin_users` table and `sessions.mfa_verified_at` column cleanly, `pnpm db:grants` confirmed the restricted runtime role, and `pnpm db:seed` created a real SUPER_ADMIN. A full HTTP walkthrough then logged in as that admin, confirmed `/admin/overview` correctly 403s before MFA verification, computed a real TOTP code against the seeded secret, verified it via `/auth/mfa/verify`, confirmed `/admin/overview` then succeeds, listed restaurants and audit logs cross-tenant, and suspended then reinstated a real restaurant — confirmed via direct SQL query against `admin_users`, `sessions.mfa_verified_at`, and `audit_logs` (actions `RESTAURANT_SUSPENDED` → `RESTAURANT_ACTIVE`, `actor_type = 'ADMIN'`), not just the HTTP response. See PHASE_REPORTS.md for the full account.

## Promotions

Coupon-code promotions with race-safe usage limits (`docs/06-business-rules.md` BR-85–BR-96, `docs/14-acceptance-criteria.md`, Phase 14) — `Promotion` + `PromotionRedemption`, restaurant self-service (`/restaurant/promotions`) and platform-wide (`/admin/promotions`) management, and full integration into the pricing engine at both quote-preview and authoritative-checkout time.

- **Zero new pricing logic.** `calculatePricing()` (`@direct-order/money`, Phase 8) has accepted a `PromotionDiscountInput` since it was written, anticipating this phase exactly the same way Phase 4's permission catalogue anticipated Phase 13. `Order.promotionId`/`couponCode`/`discountMinor` have existed unused since Phase 9. Phase 14 only had to resolve a real coupon code into that already-supported shape.
- **A real row lock, not the codebase's usual documented shortcut.** Every other lock-count-insert sequence in this codebase (`RefundService`'s INV-6 check, `OrderStateService`'s transitions) degrades to a plain, unlocked `findUnique` against the in-memory test fake, with real Postgres row-locking left honestly documented as unverified. This phase's headline acceptance criterion — "N+1 concurrent claims on a limit-N coupon yield exactly N" — is explicit enough in both the docs (`docs/02-database-schema.md` §6.3: "do not substitute an unlocked count") and the acceptance criteria that `PromotionReservationService.checkAndLock` uses a genuine `SELECT ... FOR UPDATE` via `$queryRaw`, verified against real Postgres by firing 8 truly concurrent HTTP checkout requests at a limit-1 coupon: exactly 1 succeeded, 7 got `409 COUPON_EXHAUSTED`, confirmed via a direct SQL count of `promotion_redemptions` afterward.
- **Per-customer and first-order-only limits are keyed by phone number, not `customerId`.** Guest checkout (AMB-2) creates a brand-new `Customer` row on every single order — `customerId` can never recognise a repeat guest. `PromotionRedemption.customerPhone` (denormalised, the same call `Order.customerPhone` already makes) is the actual identity signal these checks use; `customerId` is kept only for referential/audit consistency with the documented schema.
- **Two-phase validation, matching BR-86 exactly.** `POST /public/checkout/quote` resolves a coupon with a lightweight, non-locking preview (existence, active window, restaurant scope, minimum order, a best-effort usage-headroom read) — no customer identity exists yet at that endpoint, so per-customer/first-order checks are deferred. `POST /public/checkout` re-validates everything, including those two, under the real lock, inside the same transaction that creates the Order — one nested Prisma write (`tx.order.create({ data: { ..., promotionRedemptions: { create: [...] } } })`) links the redemption to its order atomically, no follow-up update.
- **Reservation lifecycle reuses the Phase 12 outbox-consumer pattern**, not a new poller: `PromotionOutboxConsumer` registers with the global `OutboxService` and confirms a redemption on `ORDER_PLACED`, releases it on `ORDER_PAYMENT_FAILED`/`ORDER_EXPIRED`. No handler is registered for cancellation at all — BR-90 ("cancellation after payment does not return coupon usage") holds structurally: a `CONFIRMED` redemption is never touched by `release`'s `status: 'RESERVED'` filter.
- **BR-95 anti-enumeration**: an unknown code, an inactive one, an expired one, a wrong-restaurant one, and one that fails its own minimum-order threshold all throw the identical `COUPON_INVALID` error — an attacker probing codes learns nothing beyond "that one didn't work." Only `COUPON_EXHAUSTED` (a genuinely-valid, already-known-real code) is more specific.
- **FREE_DELIVERY never reads its own stored value.** `Promotion.value` for a FREE_DELIVERY row is advisory only — the actual discount is resolved against the order's real delivery fee at redemption time (capped there, in `PromotionEligibilityService.toPricingDiscountInput`), so a coupon mis-configured with a huge value can never discount more than the delivery fee actually charged.
- **A real gap found in the in-memory test fake, fixed as part of this phase:** `$transaction`'s interactive-callback form had no serialization at all — concurrent calls ran fully interleaved, which would have made the "N+1 concurrent claims" test pass or fail by accident of Node's microtask scheduling rather than by the service's own correctness. Fixed by chaining every callback onto a shared queue so transactions run one at a time in the fake, the same observable guarantee real Postgres row-locking provides for the rows a test actually contends on. A `$queryRaw` stub was also added — the fake's first, since nothing needed raw SQL before this phase.
- **Verified against a real, live PostgreSQL stack this phase** — the migration applied cleanly, including a hand-written raw-SQL partial unique index on `promotions.code` (`WHERE is_active AND archived_at IS NULL`) for the one correctness-critical constraint Prisma's schema DSL cannot express. A full HTTP walkthrough created a real restaurant, a real limit-1 coupon, and fired 8 genuinely concurrent checkout requests at it — see the row-lock bullet above for the result, confirmed via direct SQL.

## Reviews

Customer reviews with Bayesian rating aggregates (`docs/06-business-rules.md` BR-117–BR-124, `docs/15-ambiguities-and-risks.md` AMB-16, Phase 15) — one review per delivered order, a restaurant response, admin moderation on report, and a live-recomputed `Restaurant.ratingAvg`/`ratingCount`.

- **Not `POST /me/reviews`.** docs/04-api-specification.md §8.4 places review submission under the authenticated-customer section, but no customer authentication exists anywhere in this codebase — guest checkout is the only path (AMB-2), the same boundary Phase 12 hit for `/me/notifications`. `POST /public/orders/:orderNumber/review` reuses the exact guest-access-token ownership check `OrderTrackingService` already uses for tracking/payment verification — the token IS the customer's only real proof this is their order, which is precisely what BR-117 requires.
- **AMB-16's recommended default, implemented as specified: reviews publish immediately** (`PUBLISHED` is the entry status), with moderation reactive on report rather than gating every review behind a queue first. `RatingAggregateService.ratingAvg`/`ratingCount` on `Restaurant` have existed, unused, since Phase 1/2 — anticipated exactly the same way Phase 8's pricing engine anticipated Phase 14's promotion support.
- **One review per order is a database constraint, not an application check.** `Review.orderId` is `@unique`; `ReviewService.submit` always attempts the insert and lets a P2002 decide, the same insert-and-let-the-constraint-decide pattern every other exactly-once guarantee in this codebase uses (Order idempotency keys, Delivery dispatch) — verified by firing 8 genuinely concurrent submissions at the same order and confirming exactly one `Review` row exists afterward.
- **XSS safety is a rendering-boundary decision, not a storage one.** Review `body` is stored verbatim; safety comes entirely from React's default text-escaping and the repo-wide lint ban on `dangerouslySetInnerHTML` — the exact same posture already applied to restaurant names and menu item descriptions (Phase 6), not a new sanitization library.
- **BR-121 ("restaurants cannot edit, hide, or delete a review") holds because no such endpoint exists** — `/restaurant/reviews` is GET (list) and POST `.../response` (one response per review, `@@unique([reviewId])`) only. There is no PATCH or DELETE on `Review` anywhere in the codebase for a restaurant principal to call.
- **Rating aggregates are recomputed synchronously, not via the debounced `rating.recompute` queue job docs/07-events-and-jobs.md names** — the same "in-process call instead of a new BullMQ job" decision every phase has made since Phase 12's own notification retry. A full `aggregate()` over a restaurant's `PUBLISHED` reviews is cheap and single-tenant-scoped; calling it directly after every submission and every moderation action means `ratingAvg`/`ratingCount` are never stale, trivially satisfying BR-123's "reconcilable against source rows" — there is nothing to reconcile, it's computed fresh every time. A restaurant with zero `PUBLISHED` reviews shows `ratingAvg: null` ("unrated"), never a manufactured `0`.
- **Bayesian blending prevents a single 5-star review from outranking an established restaurant** — `(C·m + Σratings) / (C + n)` with `m = 3.5` (the 1–5 scale's midpoint) and `C = 5` (phantom neutral reviews blended in until real volume dominates); documented, reasonable defaults, not derived from any spec. Verified live: a restaurant's first review (5 stars) produced `ratingAvg = 3.75`, matching the formula by hand.
- **BR-124 ("a minimal customer identity")**: the public review list exposes `authorFirstName` only — derived from `Customer.fullName.split(' ')[0]` at the response layer, never `phone`/`email`, matching `toPublicRestaurant`'s own explicit field-allowlist discipline.
- **A real gap found in the in-memory test fake, fixed as part of this phase:** the `customer` table had no `findMany` at all — every prior phase only ever looked up one customer at a time. Public review listing needed a batch author lookup (avoiding an N+1 over a page of reviews), which surfaced the gap; fixed the same way Phase 13 fixed `user.findMany`'s equivalent absence.
- **Verified against a real, live PostgreSQL stack this phase** — a real DELIVERED order, a real review submission via the guest token, and `GET /public/restaurants/:slug` confirming `ratingAvg: 3.75, ratingCount: 1` — the exact hand-computed Bayesian value — both from the live HTTP response and a direct SQL query against `reviews`/`restaurants`.

## Loyalty and referrals

Points earned on delivery, row-locked redemption at checkout, proportional refund clawback, admin adjustments, and referral attribution/qualification/reward — all through one append-only ledger (`docs/06-business-rules.md` BR-97–BR-116, Phase 16). Built on AMB-2's own recommended prerequisite: a lightweight, optional, phone-OTP customer account (no password) — guest checkout remains the unchanged default everywhere else.

- **The "lightweight optional account" AMB-2 always described, not a new concept.** `Customer.userId` (nullable, unused since Phase 9) and `User.phone`/`passwordHash` (nullable since Phase 3) already meant exactly this; `docs/01-domain-model.md` §5.1 already documented `OtpChallenge` as covering "phone/email verification **and customer login**". Phase 16 completes what those fields anticipated rather than inventing new infrastructure: a new `OtpPurpose.CUSTOMER_LOGIN` value reuses `OtpService` unchanged, and the existing `Session`/`AuthGuard`/`TokenService` (already generic over any `User`, not staff-specific) authenticate a customer session identically to a staff one — only a new `CustomerAccountGuard` (does this User have a Customer profile?) tells the two principals apart on `/me/loyalty*`/`/me/referrals`.
- **`POST /public/checkout` never stops working for a guest.** A new `OptionalAuthService` resolves a logged-in customer from the session cookie when present — same live user/session checks as `AuthGuard`, just returning `null` instead of throwing — so `redeemLoyaltyPoints` and permanent-identity checkout only ever apply when a real customer session exists; a guest is never blocked, and a guest who tries to redeem gets `INSUFFICIENT_LOYALTY_POINTS` rather than the request being silently ignored (AMB-2: guests neither earn nor redeem).
- **A real row lock, verified against real Postgres, mirroring Phase 14's exact precedent.** `LoyaltyRedemptionService.checkAndLock` runs a genuine `SELECT ... FOR UPDATE` on the `LoyaltyAccount` row inside the same transaction as Order creation, additionally subtracting every currently-RESERVED-but-unconfirmed redemption for that customer from the locked balance — necessary because, unlike promotions, a redemption's ledger entry is deferred to payment capture, so the lock alone isn't sufficient without also accounting for other in-flight holds. Verified live: 5 genuinely concurrent HTTP checkouts each attempting to redeem a customer's full 5-point balance — exactly 1 succeeded, 4 got `409 INSUFFICIENT_LOYALTY_POINTS`, confirmed via a direct query showing exactly one `loyalty_redemptions` row.
- **Redemption is reserved at checkout, confirmed on payment capture — the ledger itself is never touched by a reservation.** `LoyaltyRedemption` (RESERVED/CONFIRMED/RELEASED) is a separate mechanism from `LoyaltyLedger` (append-only, "never updated or deleted," BR-97): the actual debit and ledger row are written only once, at CONFIRM time (`ORDER_PLACED`), via `LoyaltyOutboxConsumer` — a RELEASED reservation (`ORDER_PAYMENT_FAILED`/`ORDER_EXPIRED`) simply never produces a ledger row at all, so no compensating "give the points back" entry is ever needed.
- **A logged-in customer's every order reuses their permanent `Customer` row** — the one checkout-flow change that gives loyalty and referrals the cross-order continuity a guest's fresh-row-per-checkout (AMB-2) cannot provide. AMB-2's own recommendation ("no" retroactive merge) is followed literally: registering never links or backfills a phone's prior guest order history.
- **Earning is idempotent by construction, not by a pre-check.** `loyalty_ledger`'s hand-written partial unique index — `(type, reference_type, reference_id) WHERE reference_id IS NOT NULL AND type <> 'ADMIN_ADJUSTMENT'` — is what makes "a duplicated `ORDER_DELIVERED` event grants points exactly once" true at the storage layer; `LoyaltyEarnService` always attempts the insert and treats a P2002 as "already awarded," the same insert-and-let-the-constraint-decide pattern this codebase has used since Phase 9. `ADMIN_ADJUSTMENT` is excluded from that constraint on purpose — an admin may legitimately adjust the same customer more than once for unrelated reasons.
- **Refund clawback is proportional and never clamps at zero (BR-103/BR-104/AMB-12).** `clawbackPoints = floor(earnedPoints × refundAmountMinor / orderPayableTotalMinor)`, written as a `REFUND_CLAWBACK` ledger entry keyed by `refundId` (not `orderId` — a single order can have several partial refunds, each clawing back its own share exactly once). A clawback is allowed to drive the balance negative; `LoyaltyRedemptionService` reads that negative balance and blocks further redemption rather than the codebase silently forgiving the debt — preserving the ledger-to-balance reconciliation invariant is worth the (rare) awkward customer state.
- **Referrals share the same ledger — "one loyalty ledger, no second point store."** `ReferralService.attributeAtSignup` resolves a code server-side at account creation only (BR-110); `qualifyOnDelivered` (same `ORDER_DELIVERED` handler earning uses) checks the referred customer's DELIVERED-order count is exactly 1 before issuing a `REFERRAL_REWARD` ledger entry to the **referrer** — idempotent via the ledger's own uniqueness, keyed by the referral's id, so a duplicated qualification event issues the reward exactly once. BR-109 (self-referral) is blocked by a hand-written database `CHECK (referrer_customer_id <> referred_customer_id)`, not only application logic; BR-108 (at most one referrer, ever) is a plain `@unique` on `referredCustomerId`.
- **BR-115: a referrer sees status and timestamps only.** `GET /me/referrals`' response is an explicit field allowlist (`status`, `attributedAt`, `qualifiedAt`, `rewardedAt`) — no name, phone, or id belonging to the referred customer is ever in the response shape, the same posture Phase 15's `toPublicReview` established.
- **A real bug found and fixed via live verification, invisible to the automated suite:** `LoyaltyAccountRepository.lockByCustomerId`'s `$queryRaw` compared a UUID column against an unqualified interpolated parameter — Postgres has no implicit `uuid = text` operator (error 42883), while Phase 14's own row-lock query never hit this because it compares a TEXT column (`code`). The in-memory test fake's `$queryRaw` stub doesn't type-check SQL at all, so all 460 automated tests passed while every real concurrent-redemption request 500'd against genuine Postgres. Fixed with an explicit `::uuid` cast; re-verified live afterward (see the row-lock bullet above).
- **Frontend:** `/customer/login` (phone-OTP, optional `?ref=` referral code), `/customer/wallet` (balance + ledger history), `/customer/referrals` (code, shareable link, referral status list) — plus a "Create a free account" link on the guest order-tracking page. No admin frontend page for `/admin/loyalty` this phase (API-only, fully tested) — the same category of gap Phase 13/14/15 each left for part of their own admin surface.
- **Verified against a real, live PostgreSQL stack this phase** — the migration applied cleanly, including two hand-written raw-SQL additions Prisma's DSL cannot express (the `loyalty_ledger` partial unique index, and `referrals`' self-referral CHECK constraint) and a partial unique index on `customers.phone WHERE user_id IS NOT NULL` (BR: one account per phone; guests may still repeat). A full HTTP walkthrough registered a referrer and a referred customer (with the referral code applied at signup), placed and delivered a real order as the referred customer, and confirmed — via the real 5-second outbox relay timer, not a manual test-only flush — that the referred customer earned exactly 5 points (₹500 subtotal ÷ ₹100) and the referrer's reward landed at REWARDED with `qualifiedAt`/`rewardedAt` populated. See the row-lock bullet above for the concurrent-redemption result.

## Support and analytics

Support cases (docs/03-state-machines.md §7.9's exact state machine, docs/06-business-rules.md BR-134–BR-140) and a daily analytics rollup pipeline (docs/01-domain-model.md §5.14) — Phase 17. Both dashboard endpoints and every case read/write go through one service each, the same "one service per aggregate" boundary `OrderStateService` established.

- **A case's `orderNumber` is resolved and ownership-verified server-side, never trusted as anything more than a lookup key.** `SupportCaseService.createForCustomer`/`createForRestaurant` look the order up by its public, human-readable number and check the caller actually owns it before ever touching the order's internal id (BR-134/BR-135/BR-148) — a cross-tenant `orderNumber` is rejected outright (422), not silently detached from the case. A case with no order at all (a general inquiry) works too.
- **BR-136 ("INTERNAL never returned to the reporter") is enforced at the query layer, not the frontend.** `SupportMessageRepository.listPublicForCase` hard-codes `visibility: 'PUBLIC'` in its own `WHERE` clause; the unfiltered `listAllForCase` is a structurally separate method only ever called from the admin/agent path — the two can never be confused at a call site. Verified live: a real HTTP response's serialized body was checked to not contain an INTERNAL note's literal text.
- **The full state machine is real, including the SLA-pause states.** OPEN → ASSIGNED (agent assigned) → IN_PROGRESS (agent's first message, INTERNAL or PUBLIC) → WAITING_CUSTOMER/WAITING_RESTAURANT (a PUBLIC agent reply — whichever party opened the case) → IN_PROGRESS (that party replies) → RESOLVED → reopened on any further reply. `firstResponseAt` (time-to-first-response) is set exactly once, on the first PUBLIC agent message, never by an INTERNAL note.
- **Attachments are private, size/type-validated, and served only via short-lived signed URLs (BR-140).** Reuses Phase 5's upload infrastructure (`StoragePort`, magic-byte content verification) rather than building parallel infrastructure — extended with `presignGet` and a PDF-aware content check (receipts/screenshots realistically need PDF, unlike branding images). `SupportAttachment` carries no `visibility` of its own, so a customer/restaurant download request looks up the parent message's visibility first — an INTERNAL note's attachment stays exactly as invisible as the note itself.
- **Rollups are computed directly from `Order`/`Payment`/`Refund`/`OrderStatusHistory`/`SupportCase` — the actual transactional source of truth — never from `AnalyticsEvent`.** This makes "rollups reconcile with source data" true by construction, not dependent on the event-ingest pipeline (an "at least once" outbox relay) never dropping or duplicating anything. `AnalyticsOutboxConsumer` separately mirrors the entire outbox stream into `analytics_events`, touching no other table — the same construction makes "analytics never mutates transactional data" true by definition rather than convention.
- **Daily boundaries are computed in each restaurant's own timezone, from scratch.** `localMidnightToUtc` (a two-pass guess-and-correct against `Intl.DateTimeFormat`-derived offsets) is correct across DST for any IANA zone; the platform rollup uses `Asia/Kolkata`, never the server's local time. Verified live and in tests: the identical instant was shown to fall in different calendar days for a restaurant in `Asia/Kolkata` versus one in `America/Los_Angeles`.
- **Both dashboards read exclusively from the materialized rollup tables, never a live scan.** `GET /restaurant/analytics/overview` and the rebuilt `GET /admin/overview` (which replaces the Phase 13 `ordersToday` live-count placeholder with real `DailyPlatformMetrics`) — `restaurantsByStatus`/`activeAdmins` remain the one deliberate exception (cheap indexed counts on small tables with no rollup equivalent). Payment/delivery success rates and support-case counts are stored as raw integer counts, never a pre-divided float.
- **Two real gaps were found and fixed mid-phase.** `SupportAttachmentService.presignDownload` existed with no controller ever calling it — attachments were uploadable but not retrievable at all; fixed by adding a download endpoint to all three support controllers. `WAITING_CUSTOMER`/`WAITING_RESTAURANT` were unreachable dead code — `postReply` already checked for them, but nothing ever set them; fixed so a PUBLIC agent reply now actually produces the transition the docs describe, making the SLA-pause semantics real rather than aspirational.
- **Frontend:** `/customer/support` and `/customer/support/:id`, `/restaurant/support` and `/restaurant/support/:id` (same shape, tenant-scoped), `/restaurant/analytics` (rollup-derived summary + daily table), `/admin/support` (queue) and `/admin/support/:id` (assign, reply with a visibility toggle, resolve, attachment download) — plus the `/admin` overview page rebuilt to show real rollup metrics.
- **Verified against a real, live PostgreSQL stack this phase.** A full HTTP walkthrough registered a real customer, placed and delivered a real order, opened a support case against it, logged in as the real seeded SUPER_ADMIN with a genuinely computed RFC 6238 TOTP code (not a test bypass), assigned the case, posted one INTERNAL and one PUBLIC message, and confirmed the WAITING_CUSTOMER transition (the exact fix above) actually happens against real Postgres — then ran the real `AnalyticsRollupService` and confirmed via real HTTP that both dashboards reconcile with what was actually just placed, delivered, and opened.

## Security hardening

A full audit against [docs/09-security.md](PRODUCT/docs/09-security.md) — Phase 18. Findings, severity, fixes, and regression tests are in [SECURITY_AUDIT.md](PRODUCT/SECURITY_AUDIT.md); this section summarizes what changed.

- **Security headers on both apps for the first time.** `@fastify/helmet` on the API, with a full-lockdown CSP (`default-src 'none'`) since it returns only JSON — there is no legitimate script/image/frame source to allow on an API surface. `apps/web/next.config.mjs` implements docs/09 §15.7's literal CSP template (allowing the CDN origin for images, the API origin for `connect-src`, and Razorpay's real checkout origin for `frame-src`) plus HSTS/nosniff/referrer-policy/permissions-policy on every route.
- **A real, previously-shipped financial-integrity bug, found by writing the one missing named attack test (docs/09 §15.5: "submit two identical refunds concurrently").** `RefundService.requestRefund`'s idempotency check ran *before* its transaction, so two genuinely concurrent identical requests could both pass it and race on the actual insert — the loser threw a raw, unhandled database error instead of returning the winner's refund. Every prior test only replayed the request *sequentially*, which can never exercise this race. Fixed with the same insert-and-let-the-constraint-decide pattern this codebase already uses for every other idempotent write, just applied at the catch site instead of relying on the pre-check alone.
- **A startup assertion now rejects a production deploy configured with a dev/localhost origin** (docs/09 §15.7) — proven previously absent by a pre-existing test that asserted the *opposite* (localhost accepted under `APP_ENV=production`) and has now been corrected to assert the safe behavior.
- **Three real rate-limit gaps closed:** `POST /auth/password/reset` and staff `POST /auth/otp/verify` had none at all — the OTP one was a genuine inconsistency, since the *request* step was throttled but the actual code-*guessing* step wasn't. `POST /public/checkout` and `POST /public/checkout/quote` (both unauthenticated) had none, despite `checkout` creating real payment-provider intents per call.
- **The 1 MB JSON body limit is now explicit and tested, not an unconfigured framework default** — which surfaced a second real bug while fixing it: the global exception filter didn't recognize Fastify's own native error shape (distinct from Nest's `HttpException`), turning a clean 413 into an opaque 500. Fixed with a dedicated error-shape check.
- **Pino's redact list gained phone/email field patterns** (docs/09 §15.9) — a phone number is now masked to its last 4 digits (dispatching on the matched field *name*, never the value's shape, so a token that happens to end in digits is never partially revealed), email fully redacted.
- **A build-time scan fails the web build if any server-only secret env var name appears as literal text in the client-shipped bundle** (`scripts/check-web-bundle-secrets.mjs`, wired as `apps/web`'s `postbuild` step) — closing docs/09 §15.8's explicit ask. `.github/dependabot.yml` added for weekly npm/github-actions/docker security-patch checks.
- **Postgres Row-Level Security — docs/09 §15.3's explicitly "optional fourth layer" — was evaluated and deliberately deferred, not implemented.** The three required layers (route guards, repository scoping, and integration tests with an explicit cross-tenant 404 assertion on every tenant-scoped endpoint across all 17 phases built so far — over 30 such tests) are real, tested, and have never been the source of a leak in this project's audit history; RLS would require a genuine cross-cutting architecture change (wrapping every Prisma call in a request-scoped transaction running `SET LOCAL app.current_restaurant_id`), not a contained addition. See `SECURITY_AUDIT.md`'s Decisions for the full reasoning.
- **Verified against a real, live Postgres/Redis stack this phase.** Every response header confirmed present with its exact configured value via real `curl` requests; a genuine >1MB body returned a real `413` with the clean error envelope; 11 real HTTP requests against the real Redis-backed rate limiter returned `429` on exactly the 11th, confirming the limiter enforces its window against real infrastructure, not just the in-memory test fake.

## Reliability and performance

Phase 19, per `docs/13-implementation-phases.md`. Full detail — including exact commands and honest limitations — lives in [DISASTER_RECOVERY.md](PRODUCT/DISASTER_RECOVERY.md), [LOAD_TEST_RESULTS.md](PRODUCT/LOAD_TEST_RESULTS.md), and [docs/runbooks/](PRODUCT/docs/runbooks/); this section summarizes what changed.

- **A real, verified backup/restore drill — `RESTORE VERIFIED`, not `NOT VERIFIED`.** docs/10 §16.4 is explicit that a backup that has never been restored is not a backup. This sandbox has no `pg_dump`/`pg_restore`/`psql`/`docker` CLI available, so `scripts/db-restore-drill.mjs` (`pnpm db:restore-drill`) uses Prisma's schema-qualified connection strings to extract real rows from the live database, restore them into a disposable schema on the same server, and verify exact row-count and SHA-256 checksum matches per table — a same-server substitute for the real `pg_dump`/`pg_restore` pair a production deploy would use, documented honestly as such. Ran clean against 233 real rows across 12 representative tables.
- **9 operational runbooks** (`docs/runbooks/`) — the exact set named in docs/10 §17.7 (`payment-failure-spike`, `webhook-failures`, `database-outage`, `delivery-provider-outage`, `queue-backlog`, `bad-deployment`, `reconciliation-mismatch`, `suspected-data-breach`, `restore-from-backup`), each with symptoms, diagnostic commands, mitigation, recovery, verification, and escalation grounded in this codebase's actual endpoints and architecture, not generic boilerplate.
- **The full data-integrity assertion suite from docs/11 §18.6, implemented, scheduled, and it immediately proved its worth.** `DataIntegrityService` runs all 6 named assertions daily (order total identity, no over-refund, no duplicate delivery per order, loyalty balance matches ledger, no order placed without a captured payment, no referral rewarded twice), recording any violation through the existing `ReconciliationIssueRepository` — so `GET /admin/reconciliation-issues` (Phase 13) surfaces them automatically, no new read endpoint needed. **Run live against the real dev database (not just the in-memory test fake), it immediately found a real false-positive bug in its own `ORDER_TOTAL_IDENTITY` check**: `Order.discountMinor` is already `promotionDiscountMinor + loyaltyDiscountMinor` combined by the time checkout persists it (`packages/money/src/pricing.ts`'s own documented `PricingBreakdown.discountMinor` semantics), so subtracting `Order.loyaltyDiscountMinor` a second time double-counted it — flagging a genuinely correct order (a real referral+loyalty checkout from earlier live testing) as a critical violation. Fixed, with a new regression test seeding exactly this combined-discount shape. The same live run also found 2 real dev-database rows with `status = DELIVERED` but no captured payment — traced via `OrderStatusHistory` (only a single `PENDING_PAYMENT` entry each, no recorded transitions) to leftover manual test-data manipulation from earlier phases' live verification, not a runtime defect; `OrderStateService`'s exhaustive transition-graph tests and the Phase 18 payment-verification regression test both confirm the real HTTP-driven path cannot produce this. Both stale/duplicate reconciliation-issue rows from this investigation were cleaned up in the dev database.
- **Queue/backlog monitoring, mapped honestly onto this codebase's real architecture.** There is no standalone BullMQ worker yet — every "queue" here is a self-starting in-process `setInterval` poller. `GET /admin/system-health` (new, gated on `payments:reconcile`) reports outbox and notification backlog depth, oldest-pending age, and dead-letter count against docs/10 §17.6's literal threshold table, rather than fabricating a queue-depth metric that doesn't correspond to anything real.
- **Graceful shutdown made consistent across all 6 self-starting schedulers.** 2 of 5 pre-existing schedulers (`LoyaltyReconciliationService`, `AnalyticsRollupService`) weren't clearing their `setInterval` on `onModuleDestroy` — `.unref()` alone stops a timer from keeping the *process* alive, but does nothing to stop a torn-down Nest module from leaving a stale timer referencing destroyed dependencies. Fixed, and the new `DataIntegrityService` was built `OnModuleDestroy`-correct from the start. A real OS-level SIGTERM was attempted against a live running server — on this native-Windows sandbox it force-terminates the process without invoking the handler at all (a documented Node/Windows limitation, not a code bug); the mechanism itself is verified via a real Nest `app.close()` in `graceful-shutdown.test.ts`, and the live-signal gap is recorded honestly in `LOAD_TEST_RESULTS.md` as open until this runs on a real Linux deployment.
- **A real N+1 found and fixed.** `LoyaltyReconciliationService.reconcile()` looped a per-customer sum query; rewritten to a single batched `groupBy`.
- **One genuine missing index found and applied to live Postgres** (a real migration, not just a schema edit): `OrderStatusHistory` had no index covering `AnalyticsRollupService`'s platform-wide daily `toStatus = 'REJECTED' AND createdAt BETWEEN ...` count. Every other model Explore initially flagged as "missing an index" turned out to already have a field-level `@unique` (Prisma/Postgres-backed) on its real lookup key — a false negative, not a real gap.
- **Frontend**: the two real `<img>` tags (restaurant logo, menu item image) converted to `next/image`, and `@next/bundle-analyzer` wired into `next.config.mjs` (`ANALYZE=true pnpm --filter=./apps/web build` to inspect).
- **Minimal Sentry wiring**, both apps — a genuine no-op without `SENTRY_DSN` (matching this codebase's established "real integration ahead of real credentials" pattern), captures 5xx exceptions in the API's global filter and worker fatal errors.
- **A real local load test** (`pnpm load-test`, autocannon — k6 is staging-only per docs/11 and this sandbox has no staging environment or standalone-binary install path) against the real dev server and real local Postgres: zero errors, zero timeouts, zero non-2xx across all scenarios. Full numbers and an honest discussion of what this does and doesn't prove vs. a real staging/k6 run are in `LOAD_TEST_RESULTS.md`.

## Money

Every monetary value in this codebase is an integer number of minor units (paise) represented as a `bigint`. There is no floating-point representation of money anywhere. `packages/money` is the only place money arithmetic happens — see its source for `toMinor`, `formatINR`, `percentageOf`, `sum`, and (Phase 8) the pricing engine, `calculatePricing`. A repo-wide ESLint rule bans `Math.round`, `.toFixed`, and `parseFloat` outside legitimate, individually-justified exceptions (grep for `eslint-disable.*no-restricted-syntax` to review every one).

## Non-negotiable invariants

These hold everywhere in the codebase, from Phase 1 onward. See [PRODUCT/IMPLEMENTATION_HANDOFF.md](PRODUCT/IMPLEMENTATION_HANDOFF.md#non-negotiable-invariants) for the full list and rationale — in short: money is server-computed and integer-only; payment success is only ever established by provider-verified confirmation; every retryable financial operation is idempotent at the database level; authorization is derived from the authenticated principal, never a client-supplied ID; audit records are append-only.
